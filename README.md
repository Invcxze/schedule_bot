# Бот расписания для Telegram

Отдельный Python-проект рядом с LMS. Использует `aiogram 3`, как Telegram-модуль LMS,
но не импортирует Django, модели пользователей и настройки основного проекта.
Источник — Google Sheets, экспортируемая в XLSX, или локальный `.xlsx`.

## Что работает

- Выбор группы по названию; сегодня, завтра и полное расписание.
- Личные чаты, обычные беседы, супергруппы и отдельные темы форума.
- Одна выбранная группа на ЛС / беседу / тему. Разовый просмотр другой группы не меняет подписку.
- Проверка источника каждые `poll_interval_seconds` (по умолчанию 1800) выполняется
  фоновой задачей Celery, а не самим ботом — см. «Celery + Redis» ниже.
- Сообщение только об изменившемся дне: новое занятие, изменение предмета,
  преподавателя, времени, аудитории или отмена. Перенос затрагивает оба дня.
- SQLite хранит подписки, контрольные копии и очередь уведомлений между перезапусками.
- Первая подписка сохраняет исходную копию без ложных уведомлений. Повторный `/group`
  с той же группой не сбрасывает контрольную копию.
- Сбой загрузки не превращается в «все пары отменены». Последняя удачная копия
  в памяти доступна с предупреждением. После перезапуска без источника просмотр
  недоступен до первой удачной загрузки; сохранённые подписки и очередь остаются.
- Пропажа/переименование **части** групп (вставленные строки, удалённый столбец,
  переименованная группа — обычное дело при правке исходной таблицы) не блокирует
  загрузку остальных: только у затронутых групп остаётся последняя известная копия
  с пометкой в чате, все остальные группы обновляются как обычно. Загрузка
  останавливается целиком только если пропала/сломалась **больше половины** ранее
  известных групп — это, скорее всего, не правка, а подмена файла или чужой лист.
- Неотправленные уведомления повторяются каждые 2 минуты отдельной задачей Celery.
  После блокировки бота подписки этого чата отключаются. После возврата используй `/subscribe`.
- Несколько листов таблицы объединяются: группа, встречающаяся на двух настроенных
  листах, получает объединённое расписание вместо ошибки (см. ниже).
- `/morning on` — ежедневная рассылка «сегодня + завтра» в заданное время
  (`morning_digest_time` по умолчанию, либо своё через `/morning at 07:30`),
  независимо от уведомлений об изменениях.
- Расписание в чате оформлено HTML-разметкой Telegram (жирный предмет/группа,
  время моноширинным шрифтом, иконки); текст из таблицы экранируется, поэтому
  `<`, `&` и подобные символы в названии предмета не ломают разметку.
  `.txt`-экспорт полного расписания остаётся обычным текстом без тегов.
- `/groups` (и `/group` без названия) показывают список группами-кнопками —
  8 на страницу (2 колонки × 4 строки), с ◀️/▶️ между страницами. Нажатие на
  группу сразу подписывает — то же самое, что `/group НАЗВАНИЕ`, с той же
  проверкой прав администратора беседы.
- `/language ru` / `/language en` — язык текста самого бота в конкретном чате/теме;
  название предмета/преподавателя/аудитории всегда как в таблице, не переводится.

## Быстрый запуск на macOS / Linux

Нужен [uv](https://docs.astral.sh/uv/getting-started/installation/).
Python 3.12 задан в `.python-version`; uv создаёт `.venv` и при необходимости
скачивает Python. Команды выполнять из этой папки, активировать окружение не нужно:

```bash
uv sync --locked
# Только если этих файлов ещё нет — существующие настройки не перезаписывай:
test -f .env || cp .env.example .env
test -f config.toml || cp config.example.toml config.toml
```

Создай отдельного бота у [@BotFather](https://t.me/BotFather) и запиши его токен в `.env`:

```dotenv
BOT_TOKEN=токен_нового_бота
GOOGLE_SHEET_URL=https://docs.google.com/spreadsheets/d/ID_ТАБЛИЦЫ/edit
```

Не используй токен действующего LMS-бота: два процесса polling будут конфликтовать.
Токен не нужно присылать в переписку. `.env`, локальная конфигурация, база и
типовые имена файлов ключей исключены из Git. Не коммить ключ под другим именем.

Сначала можно проверить приложенный Excel **без токена и без Telegram**:

```bash
uv run --locked schedule-bot check --config config.example.toml --list-sheets
uv run --locked schedule-bot check --config config.example.toml --group B26-CSE-01 --date 2026-08-31
uv run --locked schedule-bot check --config config.example.toml --group B26-CSE-01
```

Пример конфигурации ссылается на исходный файл в Downloads; на другом компьютере
поменяй `source.local_file`. При проверке бот только читает файл.

Нужен также Redis (брокер и backend для Celery). Локально — один раз:

```bash
brew install redis          # macOS; на Linux — через пакетный менеджер дистрибутива
brew services start redis   # или: redis-server --daemonize yes
```

Запуск (три процесса в отдельных терминалах, из этой же папки):

```bash
uv run --locked schedule-bot run                                          # обработка команд в Telegram
uv run --locked celery -A schedule_bot.celery_app worker -B --loglevel=info  # обновление расписания и рассылки
```

Первый процесс — это сам бот: отвечает на `/group`, `/today` и т. п.
Второй — воркер Celery со встроенным планировщиком (`-B`, beat): именно он
скачивает таблицу по расписанию, сравнивает с прошлой копией, шлёт уведомления
об изменениях и утреннюю рассылку. Без него бот отвечает на команды, но никогда
сам не напишет об изменениях и не пришлёт `/morning`. Оба процесса читают одну и
ту же `data/bot.sqlite3` и один и тот же `.env`/`config.toml`.

Программа читает `.env` из текущей рабочей папки. `--config /path/config.toml` или
`BOT_CONFIG` позволяют указать другой TOML для `schedule-bot`; та же переменная
`BOT_CONFIG` понимается и задачами Celery. Относительные пути внутри TOML
отсчитываются от его папки. Для постоянной работы нужен сервер, на котором эти
процессы не засыпают — см. «Docker / постоянный запуск» ниже.

### Зависимости и окружение

Все рабочие библиотеки, включая поддержку закрытых Google-таблиц, объявлены в
`project.dependencies` в `pyproject.toml`. `pytest` и `ruff` находятся в
`dependency-groups.dev`; uv устанавливает эту группу по умолчанию.
Точные версии и хеши зафиксированы в `uv.lock`; его нужно хранить вместе с кодом.
`--locked` запрещает незаметно менять lock-файл при запуске.

```bash
uv add имя-библиотеки
uv add --dev имя-инструмента
uv remove имя-библиотеки
# Осознанное обновление закреплённых версий:
uv lock --upgrade
uv sync --locked
```

На сервере без инструментов разработки:

```bash
uv sync --locked --no-dev
uv run --locked --no-dev schedule-bot run
```

Интерпретатор для PyCharm — `.venv/bin/python` этого проекта; зависимости меняй
через uv, не через отдельную установку в настройках IDE. Ручное создание venv и
установка через pip для этого проекта больше не нужны.

## Подключение Google Sheets

### Таблица с доступом по ссылке

Проще всего указать ссылку в `.env`. `GOOGLE_SHEET_URL` имеет приоритет над
`source.local_file` и `source.google_sheet_url` из TOML, поэтому переписывать
локальную конфигурацию не обязательно:

```dotenv
GOOGLE_SHEET_URL=https://docs.google.com/spreadsheets/d/ID_ТАБЛИЦЫ/edit
```

Альтернатива — не задавать `GOOGLE_SHEET_URL`, закомментировать `local_file` в
`config.toml` и включить:

```toml
[source]
google_sheet_url = "https://docs.google.com/spreadsheets/d/ID_ТАБЛИЦЫ/edit"
private_google_sheet = false

[parser]
sheet_names = ["1st block common"]
header_row = 2
lesson_rows = 3
```

У таблицы должен быть доступ «Все, у кого есть ссылка → Читатель» с разрешённым
скачиванием. Не делай чувствительные данные публичными ради бота: для такой таблицы
используй следующий вариант. Бот скачивает XLSX через Google export, сохраняя
объединённые ячейки; CSV не подходит. Нужна обычная ссылка `/spreadsheets/d/ID/edit`,
не ссылка «Опубликовать в интернете» `/d/e/...`.
`gid` в ссылке не выбирает лист: рабочие листы задаются в `sheet_names`.

### Закрытая таблица

Нужные библиотеки уже включены в обычный `uv sync --locked`; дополнительные extras
не требуются.

1. Создай service account в своём Google Cloud-проекте и включи Google Drive API.
2. Выдай email этого service account доступ **Читатель** только к нужной таблице.
3. Сохрани его JSON-ключ вне Git с ограниченными правами чтения.
4. В `.env` укажи `GOOGLE_APPLICATION_CREDENTIALS=/absolute/path/service-account.json`.
5. В TOML установи `private_google_sheet = true` и обычную ссылку на таблицу.

Используется только scope `drive.readonly`. Drive API экспортирует документ методом
[`files.export`](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/export)
в [формат Excel](https://developers.google.com/workspace/drive/api/guides/ref-export-formats).
У этого API есть ограничение экспортируемого содержимого 10 МБ; локальный лимит
бота для XLSX — 20 МБ. Политики организации могут запрещать сервисные аккаунты или экспорт.

Ссылка на реальную Google-таблицу и её учётные данные не были предоставлены:
эти сетевые сценарии реализованы, но должны быть проверены на твоей таблице через `check`.

## Celery + Redis

Всё, что должно происходить само по себе (без команды в чате), реализовано как
периодические задачи Celery, а не фоновый цикл внутри `schedule-bot run`:

| Задача | Расписание | Что делает |
| --- | --- | --- |
| `schedule_bot.refresh_schedule` | каждые `poll_interval_seconds` (по умолчанию 1800) | Скачивает таблицу, сравнивает с сохранённой копией каждой подписки, ставит в очередь и отправляет уведомления об изменившихся днях |
| `schedule_bot.send_morning_digest` | каждую минуту (проверка дешёвая: запрос в SQLite, без похода в источник, если для чата ещё не время) | Отправляет «сегодня + завтра» тем, у кого включено `/morning on`, чьё собственное время (`/morning at ЧЧ:ММ`) или общее `morning_digest_time` уже наступило сегодня |
| `schedule_bot.drain_pending` | каждые 120 секунд | Повторяет отправку того, что осталось в очереди после сбоя сети/лимита Telegram |

Расписание задаётся в `schedule_bot/celery_app.py` (`app.conf.beat_schedule`) и
читает `poll_interval_seconds`/`morning_digest_time`/`timezone` из того же
`config.toml`, что и сам бот, — конфигурация не дублируется. `celery_app.py`
подключается к Redis по `REDIS_URL` из `.env` (по умолчанию
`redis://localhost:6379/0`, если переменная не задана). Проверка утренней
рассылки раз в минуту, а не по единому дневному крону, — намеренно: у каждого
чата может быть своё время (`/morning at ЧЧ:ММ`), и общий тик раз в день не
дал бы это учитывать без гонки условий между несколькими крон-задачами.

Задачи используют тот же `Store`, `Sender` и `drain_outbox`, что и раньше:
поведение при сбоях, ретраях, блокировке бота и разбиении длинных сообщений на
части не изменилось — изменился только процесс, который дёргает эту логику по
расписанию.

**Не запускай больше одного воркера с флагом `-B` (beat).** Планировщик Celery
Beat сам решает, что задача «пора выполнить»; два экземпляра beat поставят
задачу в очередь дважды и разошлют дублирующиеся уведомления. Для отдельных
процессов beat/worker с несколькими воркерами вынеси `-B` в отдельный процесс
(`celery -A schedule_bot.celery_app beat`) и не указывай `-B` у воркеров.

Проверить задачи вручную, без ожидания расписания:

```bash
uv run --locked python -c "from schedule_bot.tasks import refresh_schedule_task as t; t.delay().get(timeout=30)"
uv run --locked python -c "from schedule_bot.tasks import send_morning_digest_task as t; t.delay().get(timeout=30)"
# то же самое, если всё поднято в Docker (см. «Docker / постоянный запуск»):
docker compose exec celery uv run --no-sync python -c "from schedule_bot.tasks import refresh_schedule_task as t; t.delay().get(timeout=30)"
```

## Как пользоваться

В ЛС отправь `/start`, затем `B26-CSE-01` или `/group B26-CSE-01`.
Бот сохранит группу, включит проверку изменений и покажет сегодня и завтра.
Регистр, пробелы возле дефисов и количество студентов `(27)` не важны.

| Команда | Действие |
| --- | --- |
| `/group B26-CSE-01` | Сохранить группу и включить отслеживание |
| `/group` | Список групп кнопками — нажатие сразу подписывает |
| `/today` | Сегодня для выбранной группы |
| `/tomorrow` | Завтра для выбранной группы |
| `/all` или `/week` | Полная сетка из выбранного листа |
| `/today B26-CSE-02` | Разовый запрос другой группы без смены подписки |
| `/groups` или `/groups CSE` | Список групп кнопками / поиск по части названия |
| `/subscribe` | Возобновить уведомления с текущей контрольной копии |
| `/unsubscribe` | Остановить уведомления, сохранив группу для просмотра |
| `/morning on` / `/morning off` | Включить/выключить утреннюю рассылку сегодня+завтра |
| `/morning at 07:30` | Своё время рассылки для этого чата/темы (вместо общего по умолчанию) |
| `/language ru` / `/language en` | Язык ответов бота в этом чате/теме |
| `/status` | Группа, статус, время рассылки, язык и последняя загрузка |
| `/log [N]` | Последние N строк логов bot+celery (по умолчанию 50). Только владелец — см. ниже |

`/morning on` включает ежедневную рассылку расписания на сегодня и завтра в
`morning_digest_time` (`config.toml`, по умолчанию `08:00`, часовой пояс из `timezone`).
`/morning at 07:30` переопределяет это время для конкретного чата/темы, не трогая
остальные; сбросить обратно на общее время сейчас можно только через прямую правку
БД (`UPDATE subscriptions SET digest_time=NULL ...`) — команды для сброса пока нет.
Рассылка не дублирует уведомления об изменениях: это отдельная ежедневная сводка,
использующая ту же очередь доставки с повтором при сбое. `/unsubscribe` останавливает
и её, `/subscribe` не сбрасывает её настройку (как и выбранное время).

`/language` переключает **весь текст самого бота** (подписи, кнопки, «Преподаватель»/
«Teacher» и т. п.) между русским и английским для конкретного чата/темы. Название
предмета/преподавателя/аудитории всегда берётся из таблицы как есть и никогда не
переводится. Настройка на уровне чата, не на уровне человека: в беседе с несколькими
участниками язык общий для всех. `/group` и смена группы сохраняют выбранный язык.

**`/morning` и `/language` меняет только администратор беседы** — как и `/group`,
`/subscribe`/`/unsubscribe` (см. `group_admins_only` ниже); в ЛС ограничений нет,
там администратор — сам пользователь. Команды просмотра (`/today`, `/status` и т. п.)
доступны всем независимо от этого ограничения.

Под расписанием есть кнопки просмотра сохранённой группы (только в ЛС — в беседе их
намеренно нет, чтобы участники не спамили общие кнопки; текстовые команды с `@имя_бота`
работают всегда). Длинные сообщения делятся безопасно; очень большое полное расписание
приходит `.txt`-файлом обычным текстом. Остальной вывод — HTML-разметка Telegram
(жирный текст, моноширинное время, иконки); текст из таблицы экранируется, поэтому
`<`, `&` и подобные символы в названии предмета не ломают разметку.

### Беседа / супергруппа

1. Добавь бота в беседу. Назначь администратором, чтобы Telegram надёжно давал ему
   проверять права участников; удалять сообщения или управлять участниками ему не требуется.
2. Администратор беседы отправляет `/group@имя_бота B26-CSE-01`.
3. Все участники могут отправлять `/today@имя_бота`, `/tomorrow@имя_бота`,
   `/all@имя_бота` (кнопки Сегодня/Завтра/Всё показываются только в ЛС, не в беседе —
   чтобы участники не спамили общую кнопку). Менять группу, включать/выключать
   уведомления, утреннюю рассылку (`/morning`) и язык (`/language`) может только
   администратор, включая анонимного администратора этой беседы.
4. В форуме отправь `/group@имя_бота ...` именно внутри нужной темы:
   выбор и уведомления будут привязаны к этой теме.

Команды с `@имя_бота` работают при включённом Privacy Mode; отключать его для работы
бота не требуется. Если бот назначен администратором, Telegram может доставлять ему
больше сообщений, но приложение игнорирует обычную переписку и не сохраняет её.
Подробности: [Telegram Bots FAQ](https://core.telegram.org/bots/faq).
В беседах голое название группы не обрабатывается — используй `/group@имя_бота`.
Для разрешения менять настройки любому участнику установи `group_admins_only = false`.

База хранит chat ID, ID темы, выбранную группу и копии расписания. Контакты и
история личной/групповой переписки не собираются.

## Поддерживаемая структура таблицы и важные границы

Парсер адаптирован к `Core Courses Fall 2026.xlsx`:

- строка 2 содержит группы (`B26-CSE-01 (27)`, `M26-SE-01`, `PhD`);
- слева от каждого блока групп своя колонка дня/времени;
- строка дня — `MONDAY`, `ПОНЕДЕЛЬНИК`, `ПН` и т. п. либо полная дата
  `31.08.2026`, `2026-08-31`, `31/08/2026`, в том числе Excel-дата;
- три строки пары: предмет → преподаватель → аудитория;
- объединения по горизонтали раздают лекцию всем охваченным группам;
- объединение предмета на три строки не дублируется в преподавателе/аудитории;
- пустая необъединённая ячейка не наследует чужую пару;
- время читается из своего блока, не из общего жёстко заданного списка;
- дополнительные/архивные листы не читаются, пока явно не добавлены в `sheet_names`.

**В примере несколько версий расписания.** По умолчанию читаются оба актуальных
листа первого блока — `1st block common` и `Ru Programs` (заданы в `sheet_names`);
остальные архивные/будущие листы (`... old version`, `... (block 2) ...` и т. п.)
не читаются, пока явно не добавлены туда. Некоторые группы присутствуют на обоих
листах одновременно (например, общие курсы на `1st block common` и отдельные
элективы той же группы на `Ru Programs`): в этом случае занятия объединяются —
пары из обоих листов складываются в одно расписание группы, а полностью
одинаковая пара (тот же день/время/предмет/преподаватель/аудитория), продублированная
на обоих листах, не превращается в два одинаковых сообщения. Если одна и та же
группа встречается **дважды на одном и том же листе** (реальная ошибка структуры),
загрузка по-прежнему останавливается. `/all` показывает объединённый список листов
в строке «Лист: ...». Автоматического переключения между первым/вторым блоком
семестра нет — для этого поменяй `sheet_names`.

**Основной лист — недельная сетка, а не календарь.** «Сегодня/завтра» выбираются
по дню недели в `Europe/Moscow`. `/all` показывает всю недельную сетку, а не
придуманный календарь семестра. При изменении вторника уведомление называется
«Вторник (еженедельно)», без приписывания правки произвольной дате. В сетке с
явными календарными датами уведомление относится к конкретной дате.

Оговорки вроде `ONLY ON 01/09`, `STARTS AT 18:00`, `ONLINE ON ...`, исключения,
праздники и чётность недель **не интерпретируются автоматически** — текст сохранён
в сообщении. То есть время основного слота не заменяется временем из такой оговорки.
Если нужна строго календарная логика исключений, требуется отдельный согласованный
формат данных. Для обычной недельной сетки можно задать `valid_from` / `valid_until`
в TOML: за пределами периода бот явно скажет, что блок не действует.

Для отмены пары очисти её предмет (и связанные детали), **сохранив строки времени
и заголовок дня**. Ошибочные интервалы и нарушение трёхстрочной структуры внутри
листа по-прежнему останавливают загрузку целиком (лист повреждён, а не «пара
отменена»). Пропажа группы или части заголовков дней у неё — другое дело: это не
отмена пары и не общая ошибка, а частичная деградация ровно этой группы (см. выше
и «Надёжность уведомлений» ниже). Воскресенье в недельной
сетке считается пустым, если оно явно не задано. Для других отсутствующих дней
бот пишет «нет данных», а не «пар нет». Пустой предмет означает отсутствие пары;
отдельные преподаватель/аудитория без предмета не становятся самостоятельной парой.

Цвета, размеры ячеек, счётчики студентов и координаты не участвуют в сравнении;
изменение только оформления не вызывает уведомления. Пробелы нормализуются.
Содержимое листов используется исключительно как данные, не как инструкции.

## Надёжность уведомлений

Обновлённая контрольная копия и очередь сообщений записываются одной транзакцией.
Успешно отправленные части отмечаются отдельно; ошибка отправки не теряет уведомление.
Повторный опрос неизменённого расписания не создаёт новых сообщений.
Редкий повтор возможен при аварийном завершении **между** ответом Telegram об
успехе и записью подтверждения в SQLite: Telegram не предоставляет ключ идемпотентности
для `sendMessage`. Это доставка с повторной попыткой, не гарантия exactly-once.

Изменения, внесённые и отменённые между двумя проверками, не видны. Несколько
правок между проверками объединяются в последнее состояние дня. И `schedule-bot run`
(Telegram polling), и Celery Beat запускаются в **одном экземпляре**: два поллинга
одним токеном конфликтуют, а два beat продублируют уведомления (см. «Celery + Redis»).
Воркеров Celery для обработки задач может быть несколько — дублирования там нет,
т. к. каждую задачу забирает только один воркер.
**Пропажа или переименование части групп сама по себе не останавливает загрузку**
(см. «Что работает» выше): у каждой такой группы остаётся последняя известная
копия, а её подписчики при следующем просмотре (`/today` и т. п.) видят
предупреждение прямо в чате — оно и есть сигнал разобраться, без ожидания жалоб.
Бот не переименовывает подписки автоматически (совпадение может быть случайным),
поэтому у переименованной группы нужно вручную сказать подписчикам старого имени
выбрать новое: `/group НОВОЕ-ИМЯ`. Только если пропала/сломалась **больше половины**
ранее известных групп разом (подмена файла, чужой семестр, испорченный экспорт),
загрузка останавливается целиком, как при полном сбое, — тогда проверь новый
источник через `check`.

## Логи и `/log`

Помимо обычного вывода в консоль (`docker compose logs -f bot` / `-f celery`,
см. «Docker» ниже), оба процесса — `schedule-bot run` и Celery-воркер — пишут
свой лог в файл рядом с базой (`data/bot.log`, `data/celery.log`; ротация — 2 МБ,
1 резервная копия). В Docker оба сервиса используют один volume `bot-data`, так
что оба файла видны из любого контейнера. Команда `/log [N]` в Telegram отдаёт
последние `N` строк (по умолчанию 50, максимум 500) обоих файлов вместе,
отсортированные по времени, — всегда файлом `log.txt`, а не сообщением в чат
(строки лога могут содержать символы, ломающие HTML-разметку Telegram, и файл
удобнее пролистывать, чем разбитую на части простыню текста).

`/log` — не то же самое, что `/group_admins_only`: это доступ к внутренним
логам (тексты ошибок, пути), а не к расписанию, поэтому его не даёт админство
в чате. Команда доступна только одному Telegram user ID, заданному через
`owner_user_id` в `config.toml` либо `OWNER_USER_ID` в `.env` (переменная
окружения приоритетнее, как `GOOGLE_SHEET_URL`). Без этой настройки `/log`
отвечает, что не настроена, независимо от того, кто её вызвал. Команда
намеренно не показана в меню бота (`/` в Telegram) — знает о ней только тот,
кому сказали.

## Тесты

```bash
uv run --locked pytest -q
SAMPLE_XLSX='/Users/vladhramenko/Downloads/Core Courses Fall 2026.xlsx' uv run --locked pytest -q
uv run --locked ruff check .
```

Тесты без `SAMPLE_XLSX` используют небольшие искусственные сетки и поддельный
Telegram API: ничего не отправляется в реальные чаты. Интеграционные тесты
с приложенным примером проверяют: 39 групп / 625 занятий на одном листе
`1st block common`; 59 групп / объединённое расписание `B24-RO-01` из 14 занятий
при чтении обоих листов вместе. Эти контрольные числа относятся только к
предоставленной версии файла.

`tests/test_tasks.py` проверяет ту же логику, что выполняют задачи Celery
(`refresh_and_notify`, `send_morning_digest`, `drain_pending`), напрямую —
через поддельные `service`/`sender`, без Redis и без запущенного воркера.
Redis нужен только для реальной работы (`schedule-bot run` + `celery ... worker -B`),
не для `pytest`.

## Docker / постоянный запуск

Вся база (бот + Celery-воркер с beat + Redis) поднимается одной командой:

```bash
docker compose up -d --build
```

`compose.yaml` собирает один и тот же образ трижды: `redis`, `bot`
(`schedule-bot run` — обработка команд в Telegram) и `celery` (воркер со
встроенным beat — обновление расписания и рассылки, см. «Celery + Redis» выше).
`bot` и `celery` ждут, пока `redis` пройдёт healthcheck (`redis-cli ping`), и
берут `REDIS_URL` из окружения compose (адрес сервиса `redis` внутри сети
compose), а не из `.env`, — переопределять его в `.env` для Docker не нужно.
Проверено: сборка, health-gated старт, реальный прогон `refresh_schedule` и
автоматический тик `drain_pending` по расписанию — все три сервиса действительно
поднимаются и работают вместе за один вызов, а не только по конфигурации на бумаге.

**Не запускай bot/celery одновременно и на хосте, и в Docker** — это два процесса
polling с одним токеном (Telegram ответит конфликтом) плюс два независимых beat.
Если раньше гонял `uv run --locked schedule-bot run` и
`celery ... worker -B` руками — останови их (`Ctrl+C` / `kill`) перед `docker compose up`.

В `config.toml` настрой Google-источник или добавь read-only mount Excel в оба
сервиса `compose.yaml` (`bot` и `celery` читают одну и ту же таблицу). Для закрытой
таблицы также подключи JSON-ключ read-only и задай `GOOGLE_APPLICATION_CREDENTIALS`
путём **внутри контейнера** для обоих сервисов.

```bash
docker compose logs -f bot
docker compose logs -f celery
docker compose down          # остановить; данные остаются в volume
```

База сохраняется в named volume `bot-data`, общем для `bot` и `celery`; `redis`
хранит очередь задач в своём volume `redis-data`. `restart: unless-stopped`
поднимает процессы после перезапуска Docker. Не удаляй `bot-data`, если нужно
сохранить подписки. Сервис `celery` не масштабируй за пределы одного экземпляра
(в нём встроен планировщик beat — см. предупреждение выше). Beat пишет свой файл
прогресса в `/app/data/celerybeat-schedule` (флаг `--schedule` в `compose.yaml`):
`/app` в образе принадлежит root, а процесс работает от непривилегированного
`bot`, поэтому beat не может писать в свой путь по умолчанию (текущую папку) —
не убирай этот флаг. Dockerfile запускает приложение не от root.

### Перенос существующей базы (SQLite) в Docker

Если бот уже работал напрямую на хосте и есть `data/bot.sqlite3` с реальными
подписками, первый запуск в Docker создаёт **пустой** volume — старые подписки
сами не переедут. Перенести вручную, одним разом:

```bash
sqlite3 data/bot.sqlite3 "PRAGMA wal_checkpoint(TRUNCATE);"   # слить WAL в основной файл
docker compose up -d --build
docker compose cp data/bot.sqlite3 bot:/app/data/bot.sqlite3
docker compose exec -u root bot chown bot:bot /app/data/bot.sqlite3  # cp кладёт файл от root
docker compose restart bot celery
```

`chown` обязателен: `docker compose cp` копирует файл с правами `root`, а
процессы внутри контейнера работают от `bot` — без этого шага первая же запись
в базу упадёт с `attempt to write a readonly database`.

В образ копируется uv 0.11.28. Зависимости устанавливаются через
`uv sync --locked --no-dev --no-editable` из того же `uv.lock`, что и локально —
один и тот же образ используют оба сервиса (`bot` и `celery`), меняется только
`command` в `compose.yaml`. `bot` при старте использует `uv run --no-sync schedule-bot run`;
готовое окружение не меняется и зависимости не скачиваются. Схема основана на
[официальной инструкции uv для Docker](https://docs.astral.sh/uv/guides/integration/docker/).
